# 改造卡 · 改现有的一版

> 按需加载：用户要「改」现有界面时读本文件。共享判据（通道值域、九条原理、自检九问）在 `SKILL.md`，不复制。
> 需要精确打分或量测时，走评估协议（`SKILL.md` 的指针表里已标明该读哪份）。

先分两个入口，起手完全不同——入口判断错了，改法就全错。

## 入口 A：用户已经说了改什么（执行型）

「把这几个卡片合并」「按钮换成主色」都属于这类。**关键是别顺手改别的。**

1. **先复述**：要改的是哪一处、会牵动哪些元素——一句话，让用户确认你没理解偏
2. **只动那一处**。看到别的问题先记下来，交付时提，不擅自改
3. 改完跑九问，重点看 G2（同类是否还一致）和 G4（对齐有没有被带歪）
4. 交付：改了什么 / 没动什么 / 副作用检查结果

## 入口 B：用户只说「乱」（诊断型）

1. **先量**：有 DOM 走评估协议量测；只有截图按三条估（间距 / 对比度 / 通道），并说明是估的
2. 按收益从大到小，**只动三样**：分组（间距比、容器）> 通道（字号 / 颜色 / 圆角 / 边框数量）> 层级（对比度、前景层）
3. **一次只改一个变量**。三样同时改，出了问题说不清是哪一步造成的
4. **复量**：分数没涨就回退，别靠继续加样式去救

## 动手前先看影响面

改一处常连带弄坏另一处，照着这张表查一遍：

| 你改了 | 最容易连带坏掉 | 怎么查 |
|---|---|---|
| 组内间距 | 整列高度、滚动位置 | 看组内最高的那个元素有没有被挤 |
| 删卡片边框 | 相邻卡片的边界感 | 遮住标题只看轮廓，还分得清吗 |
| 加大字号或加粗 | 同级其它层级被压平 | 只留标题，层级还剩 3 档吗 |
| 换强调色 | 状态色撞色相 | 把主按钮和报错提示放一起看 |
| 加一层容器 | 嵌套超过 2 层 | 数一下框套框的层数 |
| 改了类名 | 同名类在其它区域承载不同语义 | 全文搜索类名，确认每个出现位置是否会被新规则命中 |

## 改完的交付格式

```
## 改动 · {范围}
改了什么：{1–3 条}
没动什么：{明确列出，别让用户以为被顺手改了}
影响面检查：G1 ✓ / G2 ✓ / G4 ⚠ {具体}
复量：{改前} → {改后}（没涨就说清为什么还是要这么改）
```

## 急救表：八个症状

| 症状 | 病因 | 改哪一处 |
|---|---|---|
| 整页像糊在一起 | 组内间距 = 组间间距 | 组内压到组间的 1/3 |
| 每个模块都在抢眼 | 装饰通道太多 | 卡片删边框，只留底色差 |
| 一眼看出是拼的 | 同类元素长得不一样 | 同类签名归一，误差 0 |
| 读完不知道重点 | 没有唯一视觉主张 | 只留一个最大字号 + 一个强调色 |
| 列表越读越累 | 行距与分隔线打架 | 删分隔线，行距翻倍 |
| 灰字看不清 | 用降对比度表达「次要」 | 次要色也 ≥ 4.5:1，改用字号和位置区分 |
| 对齐总差一点 | 逐元素 margin 微调 | 全部并到同一基线，偏移 0 |
| 按钮和报错撞色 | 强调色与状态色同色相 | 状态色换一个色相 |
